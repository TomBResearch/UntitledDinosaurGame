## 6. Evidence integrity: the three blocking proofs, the JUnit format, and the PNG proof

### 6.1 Single JUnit, kept, with a transitive gate

`capture()` derives `report.testCounts` and the PASS/FAIL status from `BUNDLE/junit.xml` alone and its suite list
carries one record; the verifier re-checks report-vs-junit. That format is **kept**. The plan therefore has exactly
one junit-carrying command, and the browser results gate it:

```
pnpm test:e2e -- --suite camera   →  camera-browser-results.json   (identity artefact)
pnpm test:contract -- --task UDG-004
     reads that file and FAILS if any case failed, if the count is zero, or if the file is absent or stale
     → the junit-carrying command goes red → the bundle cannot be recorded PASS
```

## 7. Opening the scene from the owner's Mac (final, owner-ruled)

### 7.1 Ruled route

* Container start publishes **`-p 127.0.0.1:5173:5173`** — host side bound to loopback, so nothing on the Mac's
  routable interfaces is exposed.
* The **preview** container runs the dev server with **`UDG_DEV_HOST=0.0.0.0`**; the **normal/default** bind stays
  `127.0.0.1`, and nothing in the repository sets the variable.
* The `--network container:…` + `-p` sidecar route proposed in the draft is **removed** and is not to be used.
* **Preview URL: `http://127.0.0.1:5173/`. Actual port: 5173**, with `strictPort: true` so the server refuses rather
  than sliding to 5174.

Measured with the pinned Vite 8.3.6 on port 5173 in this container, which is what the mapping forwards to:

```text
$ UDG_DEV_HOST=0.0.0.0 vite …            # server.port 5173, strictPort true
  VITE v8.3.6  ready in 100 ms
  ➜  Local:   http://localhost:5173/
  ➜  Network: http://172.18.0.2:5173/  eth0        ← the bridge address Docker's -p proxy connects to
$ curl -o /dev/null -w '%{http_code}' http://127.0.0.1:5173/    → 200
$ curl -o /dev/null -w '%{http_code}' http://172.18.0.2:5173/   → 200   (this is what -p forwards to)
$ vite … (second server)                         → "Error: Port 5173 is already in use"   ← strictPort proven
```

Without `UDG_DEV_HOST`, Vite prints `Network: use --host to expose` and binds container loopback only — reachable
inside the container, unreachable through `-p`. That is the whole reason the preview container opts in.

**3a — if it is a Compose project** (its volumes are named `pi-container_*`, so it probably is): add one line to the
service and let Compose recreate it, which keeps mounts, env, network and settings intact by construction:


**3b — otherwise recreate it with the recorded values.** `stop`, never `rm`, so `docker start <container>` is always


Those two volume names are not guesses — read from this container's own mount table: `/workspace` is the named volume

`/home/node/.pi` is **`pi-container_pi-state`** (Pi session state). Take the values from step 2 rather than trusting

**What recreation does not preserve — read before pressing return.** Anything outside those two volumes lives in the
container's writable layer and is lost: the approved pinned Node at `$HOME/.local/node-v24.22.2-linux-arm64`, the
corepack pnpm shims in `$HOME/.local/bin`, the pnpm store caches under `$HOME/.local/share/pnpm` and `/tmp` scratch.
The §2.1 provisioning snippet is idempotent and takes about a minute, so re-run it after recreation; or keep the
current container alive and run the preview from it; or `docker commit` the container to an image first if you want
the provisioned toolchain preserved as a layer.

```sh
# 4 — inside the container: start the preview, then check it from the container side first
UDG_DEV_HOST=0.0.0.0 pnpm dev
#   expect the VITE ready banner, "Network: http://172.x.x.x:5173/", and the UDG_CLIENT_READY line naming the port
curl -sS -o /dev/null -w 'container-side %{http_code}\n' http://127.0.0.1:5173/

# 5 — on the Mac: reachability check, then open it
lsof -nP -iTCP:5173 -sTCP:LISTEN          # expect a com.docker listener on 127.0.0.1:5173 and nothing else
curl -sS -o /dev/null -w 'mac -> %{http_code}\n' http://127.0.0.1:5173/    # must be 200
open http://127.0.0.1:5173/

# 6 — confirm it did NOT reach the Mac's routable interface
curl -sS -m 2 -o /dev/null -w '%{http_code}\n' "http://$(ipconfig getifaddr en0):5173/" || echo "off-loopback: refused (expected)"
```

A `000`/refused result at step 5 means the mapping is missing or the container was not recreated — not a client bug.
An HTTP 200 at step 6 means the port is exposed on a routable interface: stop the server and fix the mapping.
`Host:` is `127.0.0.1:5173` in this route, so `server.allowedHosts` stays unset (and must never be `true`), and HMR
connects back through the same port so no `server.hmr` override is needed.

## 8. Mount/unmount seam (test-only), and its absence from production

`apps/client/src/dev/lifecycleHarness.ts` installs `globalThis.__udgClientHarness` with `mount(canvas)`,
`unmount()`, `cycle(n)` and `snapshot()` returning
`{ cycles, canvases, loops, meshes, observers, listeners, mounted }`. It is a **caller** of the four public
`ClientRuntime` methods, never a fifth method; `main.tsx` imports it behind `if (import.meta.env.DEV)`.

Required proofs, both in `tests/contracts/UDG-004.test.ts`:

* the **built** client output contains neither `__udgClientHarness` nor `lifecycleHarness` (byte scan of the build
  directory), and
* served from a production build, `page.evaluate(() => window.__udgClientHarness)` is `undefined`.

Playwright drives ten cycles through `cycle(10)` and writes `snapshot()` to `lifecycle-counts.json` via
`UDG_LIFECYCLE_OUT`; the DevelopmentOverlay keeps a visible mount/unmount control so the owner can repeat it by hand.
Counts, not clicks, drive the test — a lifecycle test coupled to layout is how a disposal bug turns into a flaky
test. Rejected and recorded: widening `ClientRuntime`'s surface, click-only driving, and stubbing the app.
